# 发布交叉核验与压力测试失败

`v0.1.3-security.4` 的构建运行 41488806422 在源码
`96b290c7c4c181aebbda271c30393360cbf2ddf2` 上全部通过，74 个附件回读、
23 个 ZIP、构建信息和更新脚本校验也通过。随后交叉检查发现，同一源码的
独立 Go validation 41488777222 在同节点五轮 Hysteria2 churn 的第 3 轮失败：
128 个客户端只成功建立 113 个 QUIC 会话，记录 16 次错误，其中保存的前五条
均为 CONNECTION_REFUSED；成功交换双向字节一致。6 秒清理观察从 18 个
goroutine 留下 29 个，下一轮基线仍有 1 个在线设备。不能把后续关闭节点后的
清零当作本轮自然清理通过。

该版本曾公开为 Latest；发现独立失败后已移出 Latest、改为预发布并在发布说明
首部标注失败。未升级实际生产服务器。构建工作流以后只创建并校验草稿，
必须交叉检查同一提交的全部运行后才能另行公开。

原压力测试在一个进程里同时运行客户端、代理、模拟面板和 echo，共用 Go
调度器及 GC。新增 `V2BX_STRESS_ISOLATE_CLIENTS=1` 对照模式：客户端在独立
测试子进程中运行，使用完全相同的客户端、并发、会话复用和错误断言；服务端
与 echo 仍共享父进程及同一机器 CPU。客户端错误不重试，QUIC 生产队列未修改。
计费由父进程读取；内存和 goroutine 基线仅覆盖父进程，含 echo 和模拟面板。
客户端子进程结束也不能代替父进程清理检查。

对照工作流在 GOMAXPROCS=1/2 下分别运行原模式和独立客户端模式，每个组合
计划三次测试，每次同一节点五轮。任何错误仍令该组合失败；不是失败后重跑取
成功结果。原失败保留，比较结果用于判断进程争用与真实服务端故障的边界。
在获得证据前，不声称已修复拒绝连接、内存泄漏或证明生产容量。

## 对照结果与后续验收范围

[对照运行 41494156018](https://github.com/rmomo5285-droid/V2bX/actions/runs/41494156018)
保留四组结果：独立客户端、GOMAXPROCS=2 的三次共 15 轮全部零错误、
计费一致且清理回稳；独立客户端、GOMAXPROCS=1 的第一次五轮中发生 14 次
拒绝连接；同进程 GOMAXPROCS=1 记录 8 次、GOMAXPROCS=2 第二次记录 9 次。
失败组合在首次失败测试后停止，未失败重跑取绿。

这证明调度资源和客户端放置方式影响结果，也证明进程隔离本身不能消除受限
资源下的拒绝连接。后续发布压力验收固定独立客户端、父子进程各
GOMAXPROCS=2；128 并发、轮数、速率、零错误、计费和清理断言不变。
自然空闲内存仅含服务端、模拟面板和 echo，不能与此前含客户端的 RSS 混为
同一口径。生产队列、客户端重试和默认运行时参数均未修改。

受限 CPU、同进程负载及大量完整 QUIC 握手仍有已测失败；不能宣称已修复这类
容量问题，或据此保证某种 VPS 能带多少用户。原模式继续保留复现入口和独立
对照工作流，容量实验失败与后续限定条件下的回归验收分别报告。

同一 `.4` 提交的审计分支运行 41488777130 也失败：128 并发 Hysteria2
持久场景有 12 次错误，成功交换计费等式未成立；原始计数多于仅成功确认的
交换字节，不能由此单独断言计费丢失或精确解释超时期间全部字节。


## .5 最终复查与 .6 生命周期修复

`.5` 的审计分支、默认分支和标签 Linux 验收均通过，但最终源码复查发现
Hysteria2 限速器移除后的迟到回调会 Panic；可选伪装 HTTP(S) 绑定失败会
Fatal 退出整个进程，且监听没有接入节点关闭。旧实现的回归负控确实失败。
`.5` 保持未公开草稿。`.6` 修复回调、同步绑定及失败/关闭路径，关闭普通和
升级后的连接；新增占端口、部分绑定回滚、HTTPS、端口重绑和连接清理测试。
这些修复不表示前文的 CPU 受限容量失败已解决。
